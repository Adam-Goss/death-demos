# OPNsense vs pfSense CE for the lab firewall VM

Research date: 2026-10-28. Context: [Research: OPNsense vs pfSense for the lab firewall VM](https://github.com/Adam-Goss/death-demos/issues/26), within [Plan the Proxmox attack and detection lab](https://github.com/Adam-Goss/death-demos/issues/2). Requirements come from the [build plan](../decisions/acceptance-checks-and-build-plan.md) (A2, #6, #8) and [ADR 0001](../adr/0001-isolate-the-attack-lab-behind-a-firewall-vm.md).

**Recommendation: OPNsense (CE, pinned to a tested release).** Decisive factors: first-party, documented firewall API with a savepoint/auto-rollback transaction (fits re-runnable config as code and the time-limited maintenance mode); WireGuard in core; actively maintained Ansible collection. pfSense CE would work, but its API is a community package and WireGuard is an add-on. Nothing found disqualifies either product. This is a desk comparison; **no VM was built or tested**. The M2 checks (A2) are what prove it.

## Findings against requirements

| Requirement | OPNsense | pfSense CE | Edge |
| --- | --- | --- | --- |
| Isolated zones, default-deny, IPv4 + IPv6 | Stateful filter with per-interface rules, default-deny on interfaces; 26.1 reworked IPv6 modes (Dnsmasq default, new "Identity Association" mode) ([26.1 notes](https://docs.opnsense.org/releases/CE_26.1.html)). | Equivalent capability (same class of product). Not separately verified here. | Tie. Both must be proven by the #6 probe matrix. |
| Flow/deny logging to Elastic | Remote syslog target (UDP/TCP/TLS) under System > Settings > Logging/Targets; Elastic's pfSense integration explicitly covers **both** pfSense and OPNsense, firewall + Unbound DNS + DHCP + OpenVPN/IPsec logs ([Elastic integration](https://docs.elastic.co/en/integrations/pfsense)). | Same Elastic integration; native target. | Tie. Integration is community-developed, Basic licence; use syslog (not BSD) format for hostname/timezone. Field mapping for our `lab.*` tags still to verify in M3/A4. |
| Fails closed when VM down | Architectural, not product-specific: ADR 0001 makes the firewall VM the only lab guest on the home-side network, so a stopped VM has no path. Needs M2 test (A2). | Same. | Tie (design property). |
| VPN options | WireGuard in core since 24.1 ([24.1 notes mirror](https://git.blob42.xyz/Archives/opensense-docs/src/branch/master/source/releases/CE_24.1.rst)); UI path VPN > WireGuard > Instances/Peers ([docs](https://docs.opnsense.org/manual/how-tos/wireguard-client.html)). OpenVPN/IPsec also present. | WireGuard is an add-on **package** with documented limits: minimal kernel logging, no auth/sessions, not bound to one interface/address ([Netgate docs](https://docs.netgate.com/pfsense/en/latest/vpn/wireguard/index.html)). OpenVPN/IPsec in base. | OPNsense. "VPN loss opens no route" still needs an A2 test for either. |
| NTP/DNS for lab systems | Unbound DNS + NTP built in; Elastic integration parses Unbound logs. | Same. | Tie. Not separately verified. |
| Exercise / maintenance modes (time-limited, logged) | Filter API: `firewall/filter/savepoint`, `add_rule`/`set_rule`/`toggle_rule`, `apply` with auto-revert if not confirmed within 60 s ([API docs](https://docs.opnsense.org/development/api/core/firewall.html), [savepoint text](https://github.com/opnsense/docs/blob/6700e6c2ac4876e818fb7f10666acd02a5d2bef7/source/development/api/plugins/firewall.rst.in)). Time-limited allowlist = toggle/remove a rule from the control host + schedule; config revisions give an audit trail. | No first-party API found; see next row. Firewall rule schedules exist in the GUI (not researched in depth). | OPNsense. Exact "time-limited allowlist" mechanism (rule schedule vs controller-timed removal) is an M2 design choice. |
| Re-runnable config as code (#8) | First-party REST API; Ansible `oxlorg.opnsense` (formerly `ansibleguy`) manages it via API, versioned to follow OPNsense releases, last release tested against 25.7.7_4 ([repo](https://github.com/O-X-L/ansible-opnsense), [releases](https://github.com/O-X-L/ansible-opnsense/releases)); savepoint module supports revert/cancel_rollback ([module](https://ansible-opnsense.oxl.app/modules/savepoint.html)). Terraform `browningluke/opnsense` is pre-1.0, not recommended for production by its own README ([repo](https://github.com/browningluke/terraform-provider-opnsense)). Caution: 26.1 moved NAT/interface pages to MVC/API and removed rule associations; interface assignment API was still in progress at 26.1.10, so base interface setup may need a `config.xml` seed. | REST API is the **unofficial** `pfrest` package (v2 for 2.8+); no Netgate-published compatibility matrix, and a user reports package/arch mismatches on 2.8.1 ([pfrest](https://github.com/pfrest/pfsense-pkg-restapi), [forum](https://forum.netgate.com/post/1247534)). `config.xml` restore also available. | OPNsense (first-party API, better-maintained Ansible). Collection lags OPNsense majors; pin both. |
| Proxmox VM fit | Needs ≥3 GB RAM, ≥8 GB disk; disable hardware offload in Interfaces > Settings; install `os-qemu-guest-agent` (Tier 3 plugin); i440FX or Q35 ([docs](https://docs.opnsense.org/manual/virtuals.html)). No official virtio NIC guidance found. | Netgate's Proxmox recipe: with VirtIO, disable hardware checksum offload (System > Advanced > Networking) or the VM may not pass traffic ([Netgate](https://docs.netgate.com/pfsense/en/latest/recipes/virtualize-proxmox-ve.html)). | Tie. Offload-off costs CPU; lab throughput is small. Verify in M2. |
| Licence, update/pin story | BSD 2-Clause; Business Edition is a separate paid product ([legal](https://docs.opnsense.org/legal.html)). Releases: 26.1 (2026-01-28), 26.1.11 (2026-07-01), then 26.7 ([Wikipedia](https://en.wikipedia.org/wiki/OPNsense)). | Apache 2.0 per secondary sources; one comparison site says preloading onto sold hardware is not allowed (irrelevant to a self-hosted lab, but Netgate's own EULA not verified) ([source](https://pcserverandparts.com/news/opnsense-vs-pfsense-firewall-hardware-2026/)). Latest CE 2.9.0 (Aug 2026), FreeBSD 16-CURRENT base ([release notes](https://docs.netgate.com/pfsense/en/latest/releases/2-9-0.html), [announcement](https://forum.netgate.com/topic/201188/now-available-pfsense-ce-2.9.0-release)). One user reports 2.9.0 instability and rollback to 2.8.1 (anecdote). | Slight OPNsense: point releases stay on a stable series. |

## Risks and caveats

- **Automation churn on OPNsense.** 26.1 renamed/moved NAT and rule automation pages and removed associations; 26.7 continues the NAT migration. Pin a release, test the Ansible run against exactly that, and plan upgrades as a deliberate maintenance-mode task.
- **Collection support lags.** The Ansible collection was last verified against 25.7.7, not 26.x. Check compatibility with the chosen pin before M2 or fall back to raw API calls / `config.xml` seed.
- **Docker-published ports and IPv6** are not firewall-product questions; they stay in the A2 probe matrix.
- **Unverified here:** pfSense schedule/rule features, NTP/DNS specifics, Elastic `lab.*` field mapping from firewall logs, virtio behaviour on the lab's actual Proxmox version (M0).

## Reversal conditions

Choose pfSense CE instead if M2 finds the OPNsense API/Ansible path cannot create the zones and rules reproducibly on the pinned release, or if operator familiarity with pfSense outweighs automation (then accept the pfrest dependency and test it against the pinned CE version).

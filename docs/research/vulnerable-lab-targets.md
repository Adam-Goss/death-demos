# Vulnerable Linux and SaaS-style targets

Research date: 2026-10-27. Supports [Research vulnerable Linux and SaaS-style targets](https://github.com/Adam-Goss/death-demos/issues/5). Documentation and source inspection only; no targets deployed, no attacks performed, no catalogue selected.

## Finding

A useful candidate shortlist is Juice Shop for realistic web/account workflows, crAPI for multi-service API abuse, DVWA for an explicit application-to-process exercise, and WebGoat for guided Java lessons. None should be treated as a ready-made source of complete security audit events. **Container stdout is not the same thing as application access logs, and successful application abuse need not create a new host process.** The options and observed gaps below support a later human choice.

## Logging traps and proposed evidence pairings

- **Juice Shop coverage:** its request logger is registered after several routes, including uploads. Express middleware ordering means it must not be assumed to cover requests completed earlier. Combined HTTP logs also omit request bodies and authenticated application identity. A login-abuse hunt can start with path/status/source/rate, but proving which account was affected needs explicit verification or added instrumentation. [Middleware ordering](https://github.com/juice-shop/juice-shop/blob/v20.3.0/server.ts).
- **crAPI branch drift:** inspected development nginx configuration writes request bodies to an access log under the served debug directory. Inspected stable-main configuration does not contain that custom logger. Do not promise this coverage for a stable image; do not silently enable sensitive request-body collection. [Development template](https://github.com/OWASP/crAPI/blob/b5fc307f3e5f875809b095b771108ef342a33724/services/web/nginx.conf.template), [stable-main template](https://github.com/OWASP/crAPI/blob/700f03d12a392d9e408260b4beae72ed02a4a1a4/services/web/nginx.conf.template).
- **API object access:** crAPI's cross-account challenges suggest correlating principal, object owner, endpoint, action and result. This is a proposed evidence contract, not a claim those fields already exist. Source IP and HTTP 200 alone cannot distinguish an allowed read from an ownership violation. [Challenge definitions](https://github.com/OWASP/crAPI/blob/700f03d12a392d9e408260b4beae72ed02a4a1a4/docs/challenges.md).
- **Application-to-process correlation:** a DVWA command-execution lesson suggests linking the HTTP event to the web worker's shell/child process and network event. The process initially runs in the application's container; this is **not evidence of container escape or compromise of the Proxmox host**. The source establishes shell execution; actual host sensor visibility and container attribution must be proven by the later telemetry validation. [Execution source](https://github.com/digininja/DVWA/blob/a1978a2fed195acd093010af6395f86a281537ca/vulnerabilities/exec/source/low.php).

All pairings are proposals for owned lab targets, not completed detections. App/API abuse such as cross-account access can remain entirely within an existing process. An expectation that every successful exercise produces a new process alert would reject useful application telemetry and produce misleading validation.

## Decisions now visible

1. Which initial combination matters most: web/account abuse, SaaS-like API authorization, or application-to-process correlation? Selecting all four increases integration and reset work without proving more coverage automatically.
2. What minimum fields must each exercise emit, and should missing identity/object evidence be added inside the application or at another observation point?
3. For crAPI, should the first integration use pinned stable-main/release behaviour or explicitly accept development-branch features and their logging differences?
4. What constitutes a fresh target: database only, all target-owned volumes/files, and browser/attacker-side state? How will forwarding completion be checked before reset?

These questions belong in the existing target-selection, lifecycle and telemetry decisions. Exact event samples, image compatibility, trustworthy source identity, reset completeness and resource use remain runtime validation items. The research does not establish native enterprise tenant audit support for any candidate, select an Elastic integration, or prescribe a final architecture.

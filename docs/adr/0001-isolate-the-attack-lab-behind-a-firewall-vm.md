# Isolate the attack lab behind a firewall VM

The lab deliberately runs vulnerable targets on a Proxmox host whose management interface is currently reachable from the home network. We will put a dedicated firewall VM at the lab's routed boundary, with separate attacker, per-target, and Elastic networks. It will be the only lab guest connected to the home-side network. This gives the lab one explicit enforcement point for inter-zone traffic and egress, while keeping Proxmox management outside the lab's routed paths. Proxmox guest firewall rules provide additional protection where the installed version supports them; they do not replace the routed boundary.

The operator will reach the attacker VM and Elastic management interface through a VPN on the firewall VM, available only from the trusted home-side access path. Targets can receive traffic only from the attacker VM on exercise-specific service ports and from the admin path on approved administration ports. They can send telemetry only to the ingestion endpoint, and use lab-controlled DNS/NTP. Target-to-target traffic and initiation toward the admin path, Proxmox management, other home/production networks, or the public Internet are denied. All zones use default-deny IPv4 and IPv6 policy; an unavailable IPv6 policy means IPv6 remains disabled on lab interfaces.

Exercise mode denies attacker and target Internet egress. Maintenance mode begins only after exercises stop, permits time-limited outbound access to reviewed update sources, records the change, and returns to exercise mode afterward. No public inbound path to vulnerable services is allowed. Firewall flow logs are the first network evidence source. A separate sensor VM is added only if an inline or mirrored path is proven to capture the required packets; traffic inside a target's Docker bridge is outside firewall visibility and needs host/application telemetry.

This decision sets policy, not site-specific configuration. Before implementing bridges, VLANs, firewall rules, or port mappings, record the installed Proxmox version and firewall backend, `/etc/network/interfaces`, existing bridges and VLAN capability, router/firewall topology, IPv6 state, management path, and authority to change shared networking. Validate both allowed and denied paths in both modes, including Docker-published ports and firewall failure. The detailed flow contract and verification checks are recorded in [issue #6](https://github.com/Adam-Goss/death-demos/issues/6).
